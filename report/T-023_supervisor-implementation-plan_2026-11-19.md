## 1. 方針と境界

初期段階は Node.js 標準ライブラリと注入可能な fake executor のみを使い、既存の ChatGPT ブラウザー、Bridge、ポート、認証情報、正式なセッション保存先には一切接続しない。実行許可はテスト専用の隔離ディレクトリに限定し、外部送信・自動 commit・push・PR・merge は実装しない。Codex CLI／SDK／app-server の正式接続は本計画の対象外とする。

作業データは呼び出し側が明示した専用ディレクトリに保存する。既存の `sessions`、`runs`、ポートロックとは共有しない。データ破損、結果不明、古い owner の復帰、ロック競合では安全側に停止し、不確かな副作用を自動再実行しない。

## 2. 対象ファイル

- `src/supervisor.js`：タスク状態遷移、永続化、排他、lease、heartbeat、実行結果と回復を扱う最小実装。規模が過大になる場合のみストレージを別モジュールへ切り出す。
- `test/supervisor.test.js`：Node `node:test` を用いる単体・統合・障害回復テスト。

既存の `src/queue.js` と `src/schedule.js` は記憶上の待機処理として扱い、監督処理の永続的な記録源には流用しない。

## 3. M1：状態モデルと永続化

タスクには一意 ID、冪等キー、workspace、executor、状態、試行回数、最大試行回数、runId、owner、lease 期限、作成・更新時刻、結果を保存する。状態は `pending → claimed → running → succeeded / failed / unknown / cancelled` を基本とし、再試行は安全であると確認された失敗だけ `pending` に戻す。冪等キー重複は二重投入しない。

保存は同一ファイルシステム上の一時ファイルと atomic rename を利用し、書込失敗を成功として報告しない。形式バージョンと必須フィールドを検証し、破損ファイルを空キューとして扱わず明示的に失敗させる。複数プロセスからの書込を排他制御の内側に置く。

RED：保存・再起動、重複 ID／冪等キー、破損データ、バージョン不一致、不正な遷移をテストし、実装が無いため失敗することを確認する。GREEN：最小の永続化実装を追加して再実行する。

## 4. M2：単一 owner と lease

workspace ごとに原子的なファイルシステムロックを用い、タスクの claim、状態更新、heartbeat と復旧判定を直列化する。実行単位の runId と owner token を保管し、古い owner からの更新を拒否する。lease の有効期限だけ、または PID だけを根拠に副作用を伴う処理の所有権を引き継がない。

プロセス異常終了・期限切れ後の `claimed`／`running` は原則 `unknown` として保存し、明示的な確認なしに再実行しない。ロック回復に競合または旧 owner の生存可能性がある場合、安全に停止して人による確認を要求する。誤って正式プロセスを終了させない。

RED：別々の Node プロセスによる同時 claim、heartbeat、期限切れ、旧 owner の書込、所有権不明時の停止を検証する。GREEN：必要最小限の排他と回復処理を追加する。

## 5. M3：fake executor と再試行

実行器は外部副作用を持たない注入関数とし、`success`、`failure`、`unknown` の結果を明示的に返す。成功は結果データが永続化された時だけ確定する。例外や中断で完了判定できない場合は `unknown` とする。最大試行回数の初期値は 3 とし、`failure` が明示的に再試行安全である場合だけ回数内で再投入する。

RED：成功、永久失敗、一時失敗、試行上限、例外、結果不明、冪等性、重起動時の二重実行防止をテストする。GREEN：fake executor の実行管理を加える。

## 7. 承認が必要な判断

1. 今回は fake executor に限定し、正式実行器の選定と実機接続を次段階に保留する。
2. 自動で行えるのは隔離テスト用データへの書込だけとし、製品の自律的な外部副作用は許可しない。
