## 1. 目標與明確排除

提供一個由操作者明確指定工單 ID 的最小 Python CLI，讀取 Markdown 派工表、判斷是否可以執行、建立單一執行者紀錄、在受限工作環境中啟動 Codex CLI，保存結果供人工驗收；必要時依既有欄位語意對**指定工單那一列**做安全的暫停更新。

不自動選下一張工單；不建立新狀態標籤；不自動宣告工單完成；不接 T-019 實機瀏覽器、不接正式 Bridge、不接 T-023 Supervisor 的 fake executor；不對外 commit、push、開 PR 或 merge；不安裝、升級或修改全域技能。

此文件只定義 T-027/T-028 的候選驗收契約。**權限隔離及多寫入者互斥的未決事項未核定前，不得開啟正式 Codex 任務。**

## 2. CLI 契約

- 候選入口：`python3 tools/todo_runner.py --task T-XXX --todo PATH --workspace PATH`；`--task` 不提供或不符合 `T-[0-9]+` 即以非零碼退出。是否支援字母後綴 ID 另行決定，不能靜默接受。
- 只允許**唯一、完整、正確解析**的指定 ID，檢查同檔其他表格與所有列是否有同 ID；重複、空欄或欄位數不符即拒絕。
- 禁止選取 T-025～T-028 自動執行器系列本身；禁止依檔案行序挑第一筆；必須檢查「相依」欄並能明確證實前置工單已完成，否則拒絕。
- `--todo` 必須指向明確核定、位於 workspace 內的派工檔；不得透過意外的 symlink 跳至 workspace 外；不同 repo 不能因同名 ID 混用狀態或執行紀錄。
- 原始派工表與預期目標列於啟動前先建指紋；若指紋或必要欄位在執行途中變動，不覆蓋新版本。
- 執行前顯示工作區、目標 ID、可寫範圍、sandbox、approval、子程序超時與日誌位置；未知設定直接拒絕。

## 2.1 新增／追加工單契約

- **MVP 不提供 runner 自動追加工單**：新工單由現有人工派工流程或 `dispatch-tools.py ui` 建立，維持既有 `todo_table.insert_row()` 的欄位與原始行局部更新規則；runner 只讀取已存在、明確指定的 ID。這是本草案的建議範圍，若要增加 runner 自行追加的指令，必須另行規格審查。
- 新增工單應由人工明確提供唯一 ID、需求與必要欄位，使用現行既有狀態 `待執行`；不得因 runner 被啟動而自動追加，也不得自動選取剛追加的第一筆工單。
- 追加前須核對同一份派工表所有可辨識表格中的 ID 是否重複、表頭是否受支援、插入位置與原始行錨點是否仍有效；錨點失效、重複 ID、欄位不足或未知格式就拒絕。
- 追加操作須保留所有既有工單列位元組內容；現有 UI 寫入仍有跨程序競態，不能把 `insert_row()` 的原子存檔誤認為跨程序安全交易。
- T-028 應在**暫存 fixture 副本**先透過既有追加 API 建立新工單，再確認 runner 只有收到 `--task` 指定的那筆才可啟動；同時驗證重複 ID、變更後過期錨點、錯誤欄位、新增前後非目標列位元組完全相同。正式 `todo.md` 不作追加測試。

## 3. 已確認與尚未支援的表格格式

| 類型 | 表頭判斷 | 啟動規則 |
| --- | --- | --- |
| Hadome T-025 區 | `ID／狀態／類型／需求／驗收條件與交付／相依／重試次數／暫停原因` | 候選受支援格式，T-028 fixture 驗證後才啟用 |
| 共用繁中表 | `ID／狀態／類型／需求／說明／重試次數／暫停原因` | 候選受支援格式，需逐項檢查欄位與 ID 唯一性 |
| 其他已見繁中表 | `ID／狀態／需求／說明／類型／重試次數／暫停原因／verify_method／verify_status／qa_status` | 僅在 T-028 實際 fixture 通過後啟用 |
| 含 `需求／規格` 表頭 | 已知共用 parser 可解析，但缺 `暫停原因` 的表無法完整自動復原 | 可唯讀辨識，禁止無對應欄位時自動寫暫停 |
| 日文表頭 | 尚無本輪已核實的具體實表表頭 | **預設不支援**；須提供精確欄名 fixture 並核定白名單，不採模糊猜測 |

各欄應以表頭名稱定位，而非硬編索引；未支援表頭、未跳脫的 `|`、重複欄名、列長不符、未知狀態全部 fail-closed。既有 [共用 todo_table.py](/Users/brian/.agents/skills/dispatch-task-execution/scripts/dispatch_tools/todo_table.py) 的 `parse_tables()`、`_cell_spans()`、`_locate()` 設計可作參考，但其 `edit_cell()` 只能改需求／說明，不得為此直接放寬全域 UI 編輯權限。

## 4. 正式狀態與執行期狀態分工

| 正式狀態內容 | Runner 行為 |
| --- | --- |
| 精確 `待執行` | 符合全部前置檢查後才可進入執行流程 |
| 空白 | 依既有工具顯示語意可能視為待執行，但**本 MVP 暫採拒絕啟動**；如要允許須另行核定 |
| `⏸️ 暫停`，含說明尾碼 | 不可執行或自動重試 |
| `✅ 完成`，含說明尾碼 | 不可執行 |
| 任何未知文字、縮寫或混合狀態 | 拒絕；不得自行正規化成待執行 |

- `running`、`success`、`failure`、`unknown`、`needs_review` 只允許作為**本地執行日誌的內部分類**，不能新增為 `todo.md` 的正式狀態。
- 正式工單從未經人工驗收不能由 runner 改成 `✅ 完成`；子 agent 的「成功」只代表有結果可供驗收。
- 成功且已取得 exit 0、完整最終輸出及安全檢查後，工單列原狀不變；日誌記 `needs_review`，並**禁止再次啟動同一 ID**，直到人工核對並解除記錄。這避免工單仍寫 `待執行` 時重複執行。
- 可確認失敗、未取得完整最終輸出、非零退出、中斷、逾時、可疑副作用等記為日誌 `unknown`／`failure`；若具備經核定的排他寫入條件與對應欄位，將原目標列狀態改成既有 `⏸️ 暫停`，在 `暫停原因` 寫入錯誤摘要與「等待人工決策」。**未達安全寫入條件時不能強行修改正式派工表**，留存未解決日誌並停止同 ID 後續執行。
- 不增加新的重試狀態；任何重試須由人工重新核對原結果與副作用，不能以 PID 不在、逾時或 Codex exit code 作為自動重試依據。

## 5. 單一執行者與競態處理

1. 使用每個 repo 專用且 gitignored 的執行日誌目錄，以原子建立目錄／檔案取得 runner 鎖；寫入 owner token、runId、PID、主機、指定 task、開始時間、心跳與最後更新。不同 runner 進程碰到同一鎖即拒絕。
2. lock 遺留、owner 不明、心跳逾時或程序已退出時，**不自動搶鎖或重跑**；應提供唯讀診斷與人工處置方法，保留未確認副作用的證據。
3. 已有派工 UI 的 `threading.Lock` 僅保護同一 server 程序；其 `load_lines → edit_cell → save_lines` 不是跨程序原子交易。runner 自己的鎖**不能保證**阻止既有 UI 或人工編輯器覆寫同一 `todo.md`。
4. T-027 正式寫入前必須核定共用 writer／跨程序協定；若不能修改其他 writer，則 runner 自動寫入正式 `todo.md` 的功能必須**停用（fail-closed）**，只記錄人工暫停待辦，不得聲稱「檔案寫入具互斥保證」。
5. 如核定共同 writer，變更必須比較整檔及目標列的原始位元組／雜湊，確認目標 ID、欄位與舊狀態，僅動指定列且保留 BOM、CRLF、尾換行與其餘列位元組；以同檔案系統暫存、flush／fsync、atomic rename 安全寫入。寫前與 rename 之間的競態必須由所有 writer 共同參與的排他機制封閉。
6. 對跨 repo 情境以實際派工檔 canonical path 建立可區別的 lock 與日誌，不共用 T-023 的 `tasks.json` 或 `.tasks-write-lock`。

## 6. Codex 子程序安全契約

- 僅考慮非互動 `codex exec`，明確指定 `--cd`、`--sandbox`、`--json`、`--output-last-message`；`--ephemeral` 視稽核與恢復需求核定。必須讀取結束碼及最終輸出檔；只有開始事件或部分事件不得判成功。
- 不使用 `danger-full-access`、`--dangerously-bypass-approvals-and-sandbox` 或自動核准高風險操作；approval 模式與 timeout 需有明確核定值。此版 `codex exec --help` 未列出頂層的 `-a/--ask-for-approval`，不得假定可直接傳入；T-027 須先確認設定途徑，T-028 須隔離實測生效後才可正式啟動。任何版本不支援的旗標立即失敗。
- 不能把「請勿改 todo／commit／push／PR」只寫在 prompt 當安全機制。正式任務應在專用隔離工作區運作，對正式派工檔、正式 `.git` 控制資料、憑證及正式 Bridge 環境不可寫；需在 T-028 實測可寫路徑限制、網路與權限邊界。在完成實證前禁止啟用可產生正式副作用的模式。
- 子 agent 的指示僅涵蓋核定任務，明文禁止修改派工檔、直接呼叫 commit／push／PR／merge、操作其他 repo 或正式服務。日誌留存實際命令摘要、退出碼、開始／結束時間、輸出存在性和 workspace 差異，不得包含 token 或敏感內容。
- 逾時及取消時要能處理子程序群組，並區分「已發出終止要求」與「所有子程序已確認結束」；外部副作用無法證明為零時必須進入結果不明／人工復原。

## 7. 本地紀錄與人工復原

- 建議紀錄於專案專用且加入 `.gitignore` 的路徑；採 JSONL 事件或版本化 JSON 檔。此路徑不得進 VSIX 封裝。T-027 開發時才建立資料目錄及忽略規則。
- 每次執行至少記錄：schema version、workspace canonical path、todo hash、task ID、原始列指紋、runId、owner、PID、CLI 版本、sandbox／approval、時間、退出碼、最終輸出有無、結果分類、變更檢查及人工處置需求。
- 人工復原順序：確認不明 owner 與子程序是否仍存活 → 核對 Git 工作樹、目標檔與非目標檔異動 → 檢查外部副作用及完整輸出 → 由操作者在派工表作明確驗收／暫停決策 → 保存復原紀錄 → 最後才允許對鎖／同 ID 的阻擋進行人工解鎖。嚴禁清掉鎖後自動重跑。
- Git 未追蹤或既有變更不得誤刪；所有副作用驗證需將本輪與執行前快照分開。
